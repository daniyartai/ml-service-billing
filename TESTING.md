# Отчёт о тестировании работоспособности системы (Задание №7)

## Объект тестирования

ML-сервис с биллингом в кредитах целиком, как связка компонентов:

| Компонент | Что проверяется |
|---|---|
| REST API (FastAPI) | коды ответов, форматы, аутентификация, обработка ошибок |
| Бизнес-логика | резервирование и списание кредитов, валидация, возвраты |
| База данных (PostgreSQL + SQLAlchemy) | сохранность пользователей, задач, транзакций |
| Очередь (RabbitMQ) и воркеры | постановка задачи, асинхронная обработка, отказ брокера |
| Web-интерфейс | доступность страниц, разграничение прав |

## Уровни тестирования

Проверки разделены по уровням: от изолированной логики к системе целиком.

| Файл | Тестов | Уровень | Что покрывает |
|---|---|---|---|
| `tests/test_scenarios.py` | 10 | БД и сервисный слой | работа с ORM напрямую, без HTTP |
| `tests/test_api.py` | 17 | REST API | каждый эндпоинт и граничный случай изолированно |
| `tests/test_web.py` | 8 | Web-интерфейс | доступность страниц, права администратора |
| `tests/test_e2e.py` | 2 | Сквозной сценарий | путь одного пользователя от регистрации до истории |
| `scripts/smoke_test.py` | 26 проверок | Развёрнутая система | HTTP к поднятому стенду: реальные БД, очередь, воркеры |

Разделение осмысленное: pytest-тесты отвечают на вопрос «правильно ли
работает логика», смоук-скрипт — «собраны ли контейнеры в работающую
систему». Первые ловят ошибку в коде, второй — ошибку в конфигурации,
сети или зависимостях между сервисами.

## Как запускать

```bash
# автотесты (стенд не нужен, своя БД SQLite)
docker compose exec app pytest -q

# сквозной сценарий с журналом шагов
docker compose exec app pytest tests/test_e2e.py -v -s

# смоук-проверка поднятой системы
docker compose up -d
python scripts/smoke_test.py
```

Тесты не трогают рабочую базу: `conftest.py` подменяет `DATABASE_URL` на
отдельный файл SQLite до импорта приложения. Смоук-скрипт работает с
настоящей базой и заводит одного пользователя вида `smoke-<hex>@ml-service.com`.

### 5. История операций

| Проверка | Где | Результат |
|---|---|---|
| История ML-запросов содержит все отправленные задачи | [6.1] | найдены по id, статусы совпадают |
| Сортировка: новые сверху | [6.2], `test_history_sorted_by_date` | порядок по убыванию даты |
| История транзакций сходится с балансом | [6.3] | пополнения − списания = остаток |
| Движение средств по каждой задаче | [6.4] | см. ниже |

Сверка по задачам оказалась содержательнее, чем ожидалось. Первая версия
проверки утверждала, что по неудавшейся задаче списания нет — и упала.
Разбор показал, что поведение системы правильное, а ошибочным было
ожидание: журнал хранит **обе** записи, резерв и возврат, иначе возврат
было бы невозможно проследить. Проверка переписана на итог по задаче:

- выполненная задача — итог −5;
- частично валидная — итог −5, работа всё же выполнена;
- провалившая валидацию — итог 0 при двух записях в журнале.


Смоук-скрипт на живом стенде дополнительно подтвердил то, чего не видно в
изолированных тестах: задача действительно уходит в RabbitMQ, её забирает
один из двух воркеров, результат появляется в базе и доезжает до клиента
опросом `GET /predict/{id}`. Ожидание воркера — до 30 секунд, фактически
задачи разбираются меньше чем за секунду.

## Дефекты, найденные при тестировании

Тестирование не свелось к подтверждению того, что и так работало.

**1. Частичная валидация не работала для нечисловых значений.**
Схема запроса объявляла `rows: list[dict[str, float]]`, из-за чего Pydantic
отклонял **всю** выборку с 422, если хоть в одной ячейке было нечисловое
значение. Требование задания №6 — обработать корректные строки и вернуть
некорректные — не выполнялось. При этом в доменной модели ветка проверки
нечисловых значений существовала, но была недостижима через API.
Исправлено: тип ослаблен до `dict[str, Any]`, построчный разбор целиком
отдан `MLModel.validate()`. Добавлены тесты `test_predict_partial_validation`
и `test_predict_all_rows_non_numeric_refunded`.

**2. Тесты писали в рабочую базу.**
`pytest`, запущенный внутри контейнера, наследовал `DATABASE_URL`
приложения. За несколько прогонов в боевой базе накопилось 202 учётные
записи вида `test-…@ml-service.local` и 274 транзакции. Дефект не влияет на
работу сервиса, но делает данные непригодными для анализа.
Исправлено: `conftest.py` подменяет `DATABASE_URL` до импорта приложения;
переопределить можно только явно, через `TEST_DATABASE_URL`. База очищена.

**3. В журнале администратора не отображался владелец операции.**
Колонка «Пользователь» была пуста во всех строках: схема ответа
`TransactionResponse` не содержала идентификатора пользователя, клиент
читал несуществующее поле.
Исправлено: добавлена схема `AdminTransactionResponse` с полем `user_email`;
владелец подгружается через `selectinload`, чтобы не порождать отдельный
запрос на каждую транзакцию.

**4. Кредиты числились списанными по уже проваленной задаче.**
Найдено смоук-проверкой на развёрнутом стенде — и только ей. В
`execute_prediction_task` статус `validation_failed` коммитился отдельной
транзакцией, а возврат резерва — следующей. В промежутке между двумя
коммитами клиент, опрашивающий `GET /predict/{id}`, видел невыполненную
работу с ещё списанными кредитами; на этом сорвались четыре проверки
подряд, потому что дальше расчёт баланса шёл от неверного значения.

Изолированные тесты этот дефект увидеть не могли **структурно**: в них
воркер вызывается синхронно (`_run_worker`), и обе транзакции успевают
пройти до первой проверки. Окно существует только при настоящей
асинхронной обработке, и чем медленнее база, тем оно шире.

Исправлено: статус неуспеха и возврат сведены в одну транзакцию — теперь
поведение соответствует тому, что и раньше утверждала строка документации
(«списание + результат атомарно»). Инвариант закреплён тестом
`test_no_intermediate_state_with_unrefunded_charge`: он подписывается на
события коммита и падает, если хоть один из них делает видимой задачу со
статусом неуспеха и ненулевым `charged`. Проверено, что на прежнем коде
тест действительно падает — с диагностикой `[('validation_failed', 5.0)]`.

Попутно исправлена ошибка в самой смоук-проверке: ожидание задачи
завершалось по условию «статус не `new`», из-за чего могло вернуться
промежуточное `running`. Теперь скрипт ждёт конечного статуса.

**5. Технические подробности утекали в интерфейс.**
При остановленном RabbitMQ пользователь видел `[Errno -2] Name or service
not known`. Исправлено: наружу уходит объяснение на человеческом языке,
подробности пишутся в лог с идентификатором задачи. Тест
`test_refund_when_publish_fails` дополнен проверкой, что текст ошибки
брокера не просачивается в ответ.

## Выводы

Система работает как единое целое: сквозной сценарий проходит от
регистрации до сверки истории без ручного вмешательства, а на развёрнутом
стенде подтверждается и работа инфраструктуры.

Ключевое свойство биллинга — кредиты списываются только за выполненную
работу — проверено с четырёх сторон: провал валидации, ошибка воркера,
недоступность очереди, нехватка средств. Во всех случаях баланс
восстанавливается, а в журнале остаётся след обеих операций.

Тестирование выявило пять дефектов, четыре из которых относятся к
функциональности, заявленной в предыдущих заданиях как готовая. Это и есть
главный практический вывод: без сквозной проверки расхождение между
«написано» и «работает» остаётся незамеченным — особенно там, где
изолированные тесты проверяют компоненты по отдельности и потому не видят
ошибку на стыке (как в случае со схемой запроса, где строгий тип поля
отменял логику валидации, написанную уровнем ниже).

Отдельный вывод — о ценности разных уровней проверки. Дефект №4
принципиально недостижим для изолированных тестов: он существует только
при настоящей асинхронной обработке, а в тестах воркер вызывается
синхронно. Его нашла проверка на развёрнутой системе, где между постановкой
задачи и результатом действительно проходит время. Обратное тоже верно:
инвариант, вскрытый этим дефектом, невозможно надёжно проверить снаружи по
HTTP — гонка воспроизводится не всегда, — поэтому он закреплён
детерминированным тестом на уровне транзакций. Один уровень тестирования
не заменяет другой.

## За рамками проверки

Осознанно не проверялось:

- нагрузка и параллельная работа нескольких воркеров на одной задаче;
- поведение при обрыве соединения с БД в момент списания;
- модерация пополнений администратором — не реализована (необязательная
  часть задания №6);
- фронтенд-сценарии в браузере автоматически: проверены вручную,
  автотесты покрывают доступность страниц и права доступа.
